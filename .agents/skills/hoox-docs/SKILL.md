# Hoox 文档维护

先读取仓库根 `AGENTS.md` 和 `docs/AGENTS.md`。`docs/AGENTS.md` 是文档分类、权威关系、生命周期和写作规则的事实源；本 Skill 只定义执行流程，不重复建立第二套规范。

## 控制范围

- 普通开发任务只检查受改动行为及其直接索引，不顺带审计整个 `docs/`。
- 只有用户明确要求文档审计、重组、Roadmap 清理或全库复核时，才执行语料库级审计。
- 审阅或审计任务默认只报告问题；用户明确要求修改、修复或整理时才写文件。
- 不修改 `runtime-ts/vendor/` 中的第三方源码、`node_modules/`、生成产物或测试快照；应修改其事实源并重新生成。Spike 与验证记录可修正失效入链，但不顺手现代化其时点正文。

## 编辑前先分类

将目标内容归入 `docs/AGENTS.md` 定义的当前说明（含 `architecture/` 设计约束）、目标规范、实施计划或时点证据。分类不清时，根据读者用途和权威范围判断，不按目录名机械决定；改变文档权威性质或把当前入口降级为历史入口时，必须在修改说明中明确这一变化。

解释当前行为时，以当前说明作为读者入口，并用代码、配置和测试验证。不得让计划、Spike 或验证记录代替当前说明。`architecture/` 保存当前设计约束，Plan 保存实施顺序，证据记录特定时间点的验证；选择理由写入 PR 描述或提交信息。

## 保留完整命题

修改文字前识别并保留相关的：

- 主体和动作；
- 条件、时机与顺序；
- 必须、可以、禁止及例外；
- 所有权、副作用、失败方式与后果；
- 安全、兼容、持久化和恢复约束。

仅在代码和结构不能直接表达这些事实时增加说明。删除逐行控制流翻译、重复目录、实现流水账、评审对话和无法从当前仓库解析的会话引用。当前说明使用 HEAD 视角；Plan 和时点证据中的必要历史叙述保留在其所属文类中。

## 工作流

1. 确认任务范围、适用的 `AGENTS.md` 和目标文档类别。
2. 阅读文档所描述的代码、配置、测试和直接子文档；验证行为动作，不能只搜索到同名类型或字段就判定正确。
3. 明确读者为什么来到该文档、读完能解决什么问题、该文档拥有什么事实；没有明确读者或独立职责时，不新增文档。
4. 先更新事实拥有者，再更新摘要、索引、生成内容和其他引用。一个事实保留一个主要归属，其他位置只保留完成局部任务所需的契约或链接。
5. 移动、重命名、完成、替代或删除文档时，原子更新状态、当前权威、替代关系、索引和全部入链。
6. 计划完成前，必须把最终行为迁入当前说明；已完成、已替代或已放弃的计划退出主要导航。Roadmap 不承担详细任务清单或历史状态账本。
7. 对全库审计，先分类和报告，再应用明确修复；区分可机械证明的路径、名称和参数问题，与需要语义判断的行为、数量、否定保证和替代目标。
8. 运行与改动范围相符的检查，检查最终 diff 没有误改第三方、生成或历史内容。

## 验证与交付

至少运行：

```sh
pnpm format:check
pnpm lint
git diff --check
```

命令、配置、接口、提示词、工具描述或生成内容发生变化时，补充直接覆盖该表面的验证。最终说明修改了哪些权威文档、发生了哪些生命周期变化、保留了哪些历史内容，以及实际执行的检查。
