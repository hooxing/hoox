# Hoox 文档约束

本文件是 `docs/` 内文档分类、权威关系、生命周期和写作规则的事实源。执行文档任务时使用 `.agents/skills/hoox-docs/SKILL.md`；根 `AGENTS.md` 的安全、验证、ADR 和提交规则继续适用。

## 第一原则

文档的价值是帮助明确读者完成任务、理解当前系统或追溯决策，而不是保存编写过程。每篇文档都应能从开头和所属索引看出：谁在什么场景下阅读、读完能解决什么问题、它对哪些事实具有权威性。没有独立读者或事实归属时，优先改进现有文档，不新增文件。

当前行为必须能从当前说明直接获得，并由代码、配置和测试验证。读者不应通过拼接 ADR、实施计划、Spike 或验证记录推导现状。

## 文档分类与权威范围

| 类别 | 主要位置 | 回答的问题 | 维护方式 |
| --- | --- | --- | --- |
| 当前说明 | `architecture/`、`development/`、`reference/`、`operations/`、`maintainers/`、`project-status.md` | 系统现在是什么、如何使用和维护 | 行为变化时同步更新 |
| 目标规范 | `specs/` | 跨模块能力必须达到什么目标和约束 | 明确已实现与目标范围，链接当前说明和 ADR |
| 架构决策 | `decisions/` | 为什么选择当前方案以及放弃什么 | 已接受结论不改写，变化时新增替代 ADR |
| 实施计划 | `plans/` | 准备或曾经按什么顺序实施 | 必须声明生命周期；完成后迁移当前事实并退出主要导航 |
| 时点证据 | `verification/`、`spikes/` | 某个提交、环境或时间点验证了什么 | 保留证据上下文，不自动视为持续保证 |
| 历史资料 | `archive/` | 哪些失效资料仍值得追溯 | 明确历史状态和当前替代入口，不承担现行指导 |

分类以用途和权威范围为准，不因文件暂时位于某个目录就忽略内容性质。混合大量当前说明、计划和历史过程的文档应拆分；少量辅助内容可以保留在明确命名的章节中。

## 一个事实一个主要归属

文档只完整描述自身主题。直接子主题只说明目的、责任和高层行为，并链接到其事实拥有者；测试机制、夹具和局部实现细节放在最低拥有层。当前说明可以重复局部使用者必须知道的行为、失败和后果，但不得复制架构理由、历史过程、完整目录或其他文档的主体内容。

生成目录和派生文档不得手工修改。修改 JSDoc、配置定义、生成器或其他事实源后重新生成，并在同一变更中提交结果。

## 文档形态

- 教程引导明确读者按依赖顺序完成一个可观察结果，只引入当前步骤所需概念。
- 参考文档在明确范围内支持查找，不要求顺序阅读。
- 同一文档不应同时承担大篇幅教程和参考职责；必要时拆分，次要形态较小时使用清晰章节。
- 分类索引不能只有文件名列表，应说明什么情况下阅读每个子文档以及它回答什么问题。

## 当前说明的写作规则

当前说明从仓库 HEAD 的视角描述事实，不叙述“本次修改”“上一轮评审”“后续 PR”“此前设计稿”等编写过程。保留当前读者需要的：

- 行为、条件、时机和顺序；
- 必须、可以、禁止、负面保证和例外；
- 所有权、副作用、失败方式和后果；
- 安全、兼容、持久化、恢复与运维限制。

删除代码已经直接表达的逐行控制流、测试步骤解说、重复说明和无权威来源的状态汇报。历史叙述在 ADR、Plan、Spike 和验证记录中可以保留，但引用必须能从当前仓库或明确外部来源解析。

不同表面的必要内容：

- 公开 JSDoc 说明调用方可见的返回差异、失败、副作用、所有权、时序、取消和持久性。
- 内部注释只解释非显而易见的不变量、竞态顺序、安全边界、所有权和失败语义。
- README 说明配置、行为、限制、失败、扩展点和使用入口，不重复生成目录和其他包职责。
- 测试注释只解释非显而易见的夹具、真实入口、平台适配或间接观测理由。
- Prompt、Tool description、错误诊断和 UI 文案属于行为；修改时检查模型或用户可见结果。

精简前先枚举完整命题。字数减少本身不是改进，不得删除条件、强制程度、例外、失败或后果。

## Plan、Roadmap 与 ADR 生命周期

新建或修改实施计划时，必须明确使用以下一种状态：

| 状态 | 含义 |
| --- | --- |
| 草案 | 尚未接受，可以大幅调整 |
| 进行中 | 当前实施顺序的有效依据 |
| 阻塞 | 方向仍有效，但存在明确外部或技术阻塞 |
| 已完成 | 实现、验证和当前说明已经收口 |
| 已替代 | 被新 Plan 或 ADR 取代，并明确替代入口 |
| 已放弃 | 明确停止，不再作为后续实施依据 |

计划只有在最终行为已写入当前说明、相关验证存在且当前权威链接明确后才能标为已完成。已完成、已替代和已放弃的计划不得继续出现在主要导航的活跃区域。修改已有计划时若缺少状态，应在同一变更中补齐；不要求仅为格式一次性改写全部历史计划。

Roadmap 只保留战略方向和阶段 Gate，不维护详细任务清单或可能长期失真的复选状态。当前成熟度和生产缺口归 `project-status.md`，实施顺序归活动 Plan，历史路线归 `archive/`。

新增 ADR 时必须搜索相同决策、机制和被拒绝方案，建立完整或部分替代关系。保留仍能约束安全、所有权、协议、持久化、失败语义或防止高概率错误重现的记录；低未来决策价值的实施过程可降级为历史，但不得仅按年龄、长度或数量处理。

## 修改与验证

普通代码任务只检查受影响行为及其直接索引；全库审计必须由用户明确要求。审计先报告分类、重复、矛盾、缺失当前说明、过期入口和生命周期问题，再执行用户授权的修改。

移动或重命名文档前搜索所有入链；移动必须同时完成旧位置移除、新位置建立、索引和入链修复。命令、路径、端口、环境变量和协议必须从当前仓库验证，不能凭记忆更新。

至少执行 `pnpm format:check`、`pnpm lint` 和 `git diff --check`。文档涉及配置、命令、公开接口、提示词、生成内容或用户可见行为时，运行直接覆盖该表面的检查。最终说明实际检查，不把未运行的 Gate 写成已验证。
