# ADR-0015：进程生命周期、严格配置与薄装配入口

- 状态：已接受
- 日期：2026-07-26
- 决策者：M2 进程骨架实施审阅
- 关联任务/PR：M2 进程生命周期骨架，`feat/m2-process-lifecycle-skeleton`
- 替代关系：无

## 背景

API、Agent Worker 和 Scheduler 已有不同程度的业务能力，但没有统一的生产进程边界。若每个应用自行读取 `process.env`、注册信号、决定关闭顺序和伪造缺失依赖，后续真实数据库、消费者和网络监听装配会产生三套失败语义，也可能让开发 Fake 被误用于生产。

本阶段只建立可测试的进程骨架，不实现真实 PG Worker Repository、Run dispatch、清理消费者、生产身份供应商或模型调用。

## 决策驱动因素

- 缺失、拼错和多余的关键环境变量必须在任何外部连接前失败；
- 配置错误和日志不能包含密钥值、连接串或底层解析异常；
- `SIGTERM` 与 `SIGINT` 必须停止接收、排空在途操作并按确定顺序关闭资源；
- 重复信号、重复关闭及迟到的异步结果不能改变最终状态；
- 应用入口应明确表达真实依赖尚未装配，不能以空消费者或 Fake 宣称生产就绪；
- 相同实现必须在 Linux 部署环境和 Windows 开发环境工作。

## 备选方案

### 方案 A：三个应用分别实现配置和信号处理

局部代码直接，但关闭时序、超时、错误脱敏和环境差异会逐渐分叉，故障测试也需要重复维护。

### 方案 B：只依赖容器编排发送信号并强制终止

实现最少，但不能证明 HTTP 请求、执行中的 Attempt 或资源提交已经排空；强制终止也无法提供稳定的关闭失败分类。

### 方案 C：共享进程运行包，应用只声明配置和装配器

共享包统一严格配置、在途操作、信号和健康状态；每个应用保留自己的配置结构与真实装配接口。代价是新增一个基础包，并要求后续资源显式登记关闭顺序。

## 选择

采用方案 C，新增 `@cube-runtime/process-runtime`。

### 配置边界

1. 必须显式提供 `RUNTIME_ENV=development|test|production`，不做默认回退。
2. 应用先从宿主环境投影自己声明的键，再交给严格解析器；解析器拒绝投影视图中的未知键、缺失必填键和非法值。`PATH`、CI 等宿主键不进入应用配置。
3. 解析错误只包含稳定分类和变量名。秘密字段的值、数据库连接串、URL 凭据和解析库消息都不进入异常。
4. `DEV_AUTH_ENABLED=true` 只允许 development/test。生产环境即使其他配置完整也拒绝启动；开发身份仍必须通过显式装配器消费，不能成为共享包的隐式认证实现。
5. API、Worker 和 Scheduler 只声明本进程需要的变量。`DATABASE_BOOTSTRAP_URL`、迁移角色和 MinIO root 凭据不进入服务进程。

### 生命周期边界

1. 首次关闭立即切换为 draining 并执行 `stopAccepting`，之后等待已登记的在途操作落定。
2. 在途操作成功或失败都可排空；调用方仍收到原始操作结果，生命周期不吞掉业务失败。
3. 资源按装配器声明顺序串行关闭。单个资源失败后继续关闭后续资源，最终只暴露稳定的资源名级错误。
4. 整体关闭受 1 毫秒到 10 分钟的稳定超时约束。超时后迟到的清理完成或失败不能覆盖已确定的超时结果。
5. `SIGTERM`、`SIGINT` 和显式 `close()` 共用同一个记忆化关闭 Promise；重复调用幂等。库不调用 `process.exit`，退出码和宿主策略由真正的最外层部署入口决定。
6. `/live` 语义只反映进程仍在运行或正在停止，不访问外部依赖；`/ready` 在 draining 后立即失败，并对已注入的依赖探针逐项安全归一化。

### 薄入口与生产拒绝

API、Agent Worker 和 Scheduler 分别公开类型化配置解析及 `start*Process`。启动必须注入 `ServiceAssemblyFactory`；缺失装配器固定返回 `ASSEMBLER_MISSING`，装配异常固定返回 `ASSEMBLY_FAILED`。本阶段不提供默认装配器、内存生产回退或自动网络监听，因此“配置可解析”不等于“服务可部署”。

## 理由

关闭顺序和配置失败是跨应用的运维不变量，适合集中实现；具体依赖和配置形状属于应用边界，仍由各应用声明。强制注入装配器使未完成的生产依赖在启动时可见，避免把测试 Fake 变成隐式运行模式。

## 影响

### 正面影响

- 三类进程共享可故障注入的关闭状态机和脱敏错误；
- 开发、测试、生产配置边界明确，拼错变量不会被静默忽略；
- 后续 PG pool、HTTP listener、队列消费者和遥测资源有统一登记位置；
- Linux/Windows 测试和 Linux 最小容器门禁能提前发现平台差异。

### 负面影响与成本

- 新增生产依赖时必须同时决定 readiness 探针和确定的关闭顺序；
- 严格配置会使遗留或多余变量立即失败，部署清单需要按应用投影；
- 当前薄入口没有真实 assembler，三个进程仍不能作为完整生产服务启动。

### 安全与运维影响

- 部署平台的强制终止宽限期必须大于 `PROCESS_SHUTDOWN_TIMEOUT_MS`；
- 信号失败回调只能记录稳定错误分类，不能序列化原始配置或依赖异常；
- 健康端点的 HTTP 路由仍由真实应用装配负责，本包只提供状态语义，不能另起管理端口绕过鉴权和网络策略。

## 验证

- 配置表测试覆盖三种环境、未知/缺失/非法变量、生产开发身份拒绝和秘密不泄漏；
- 生命周期故障注入覆盖停止接收、在途成功/失败、串行关闭、资源失败继续、超时、重复信号和重复关闭；
- 三个应用入口覆盖配置成功但装配器缺失时拒绝启动；
- GitHub Actions 在 Ubuntu 与 Windows 执行同一组进程测试，Ubuntu 额外构建最小非 root 容器并执行启动/关闭门禁；
- 全量 clean-vendor、依赖审计和敏感信息扫描。

## 可逆性与回退

本阶段没有数据库迁移、公开网络协议或持久数据变更，可删除薄入口和共享包回退。真实部署一旦依赖这些错误码、关闭顺序和配置键，修改它们需要部署迁移和双版本观察窗口。
