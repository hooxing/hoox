# ADR-0112：受管 Skill 管理发布与独立权限面

- 状态：已接受
- 日期：2026-08-05
- 决策者：Runtime 维护者
- 关联任务/PR：管理员发布 Skill 到技能中心
- 替代关系：补充 ADR-0094、ADR-0095 与 ADR-0107

## 背景

ADR-0094 把公开目录写权限保留给受信发布流程，但现有实现只有 development 专用的固定 PPTX fixture 命令，
不能接收一般 Skill 包，也没有提交、复核、发布、撤销和审计闭环。普通 API Runtime 只有目录读取及用户安装权限，
不应因新增管理功能获得市场写权限；Migrator 则是离线 DDL 身份，不能进入常驻发布服务。

Skill 包可能包含模型指令、脚本和二进制资源。首版能够确定性验证结构与内容完整性，但尚没有恶意软件扫描、脚本
行为分析或发布者信任等级，因此不能把通过结构校验表述成“安全”。生产浏览器身份接入由同源身份网关负责；管理
API 只接受独立 audience 的短期 JWT，数据库再以平台运营角色完成二次授权。

## 决策驱动因素

- 普通 Runtime、Migrator 与管理发布进程必须保持不同的数据库和对象存储权限；
- 发布者不能自审，最终公开和硬撤销必须由管理员执行；
- 重试、并发操作和提交结果未知不能产生重复目录版本或覆盖新状态；
- 对象存储与 PostgreSQL 无法形成分布式事务，必须定义可恢复的提交顺序；
- 上传内容、JWT、对象引用和内部错误不得进入公开响应或日志；
- 管理前端需要独立部署，不能混入普通用户工作台的公开导航和凭据边界。

## 备选方案

### 方案 A：在普通 API 和 Web 中增加管理员路由

可复用现有进程与前端，但普通 Runtime 需要获得市场写 ACL 和发布 S3 凭据；路由隐藏、JWT audience 或 UI 条件
渲染都不能消除进程被攻陷后的横向权限，故不采用。

### 方案 B：继续用运维脚本直接写目录

实现最少，但缺少提交/复核职责分离、幂等状态机、统一包校验和可查询审计；人工 SQL 或脚本重试也容易形成对象与
目录漂移，故只保留为灾难恢复手段，不作为日常上架流程。

### 方案 C：独立管理 API、管理 Web 和专用发布身份

新增受限常驻进程与独立前端；JWT 只证明用户身份，平台运营角色来自 PostgreSQL。内容先写入摘要寻址的私有对象，
再在单个串行化数据库事务内写申请、命令、审计和公开目录。

## 选择

采用方案 C，并限定以下边界：

1. 新增 `publisher`、`reviewer`、`admin` 三种平台运营角色。角色由受控数据库运维流程配置，不通过本管理 API
   提升；停用 operator 行立即阻止后续请求。
2. 状态机为 `draft -> submitted -> approved -> published -> revoked`，复核也可令 `submitted -> rejected`。
   `publisher` 创建并提交；`reviewer` 只能审核他人申请；`admin` 负责公开和撤销，并可执行前序操作。
3. 所有写请求要求调用方幂等键；状态推进同时要求 `expectedVersionToken`。数据库以 actor+幂等键保存命令结果，
   用 advisory lock、行锁和 SERIALIZABLE 事务收敛首次并发竞争。
4. 包必须包含严格 UTF-8 的根级 `SKILL.md`；最多 256 个文件、总计 32 MiB、入口最多 64 KiB。路径规范化后
   禁止绝对路径、遍历、控制字符、双向/零宽字符、大小写折叠冲突和文件/目录前缀冲突；拒绝已知原生可执行扩展、
   私钥标记和常见云访问密钥标记。所有文件及规范清单都计算 SHA-256。
5. 上述检查只产生 `security_status=restricted`，不宣称内容可信。管理员必须结合已声明的来源地址与不可变
   revision、SPDX 许可证、入口正文和文件摘要人工复核；未声明上游来源的本地上传以包摘要标识实际字节。自动恶意
   内容分析另行设计。
6. 对象按内容摘要使用条件写入，并在 HEAD 后完整 GET 校验；随后 PostgreSQL 原子写入申请事实。数据库失败时不
   删除可能已被并发事务引用的稳定对象，允许留下不可见孤儿并由后续生命周期作业回收；同内容重试复用对象。
7. 发布事务原子创建公开 `skills`、`skill_versions` 和文件清单；硬撤销把精确版本标记为 revoked。首次发布必须
   同时设为推荐版本，避免 active Skill 指向空推荐版本。
8. 管理 API 使用独立 JWT audience、独立数据库登录、独立 S3 凭据和单独监听端口。数据库发布角色无继承、无
   owner、无角色成员、无建库/建 Schema/临时表能力，对 Tenant、Thread、Run 等 Runtime 表保持零 ACL。
9. 管理 Web 只调用同源 `/v1/admin/skill-submissions`。development 的 Vite 代理可从服务端环境注入开发 token；
   token 不进入静态资源。production 必须由同源身份网关剥离客户端伪造的 Authorization，并基于已登录管理会话
   注入独立 audience JWT。

## 理由

独立进程把“目录读取/安装”和“平台内容发布”分成可审计的故障域，即使普通 API 或 Worker 被攻陷，也无法获得
发布数据库 ACL 或 S3 写凭据。领域层与 PostgreSQL 适配双重校验角色、自审规则、状态和 CAS，避免测试装配或未来
调用方绕过其中一层。内容寻址的先对象后事务方案不需要分布式锁；代价是安全的孤儿对象，而不是数据库引用不存在
对象或错误删除已提交对象。

## 影响

### 正面影响

- 具备创建、提交、复核、发布、撤销、列表和详情预览的完整管理员操作面；
- 每次状态变化都有 actor、前后状态、理由和版本令牌审计，并支持稳定幂等回放；
- 公开目录继续只暴露已发布、未撤销的精确版本，普通 Runtime 权限不扩大；
- 上传文件在进入事实源前完成规范化、摘要和对象完整性验证。

### 负面影响与成本

- 新增管理 API/Web 两个部署单元、数据库角色、JWT audience、S3 凭据和运维告警；
- 创建请求以 Base64 JSON 传输并在进程内校验，首版适合不超过 32 MiB 的低频运营发布，不适合大包或高并发；
- 数据库失败可能留下不可见的内容寻址对象，需要后续按无引用保留期回收；
- 自动恶意软件与行为分析未实现，`restricted` 版本仍依赖人工复核和既有 Sandbox/工具权限边界。

### 安全、数据与运维影响

- `platform_skill_operators` 及四张发布事实表强制 RLS；发布连接每个事务设置可信 `app.user_id`；
- 生产管理服务拒绝普通 API audience、开发身份变量、明文 S3 endpoint 和可注入 Fake 的装配入口；
- 日志只记录稳定失败分类与 request ID，不记录 Authorization、正文、入口指令、对象键或 provider 错误；
- operator 初始化/变更必须走数据库运维审计；生产入口不得携带 Database Admin 或 Migrator 凭据；
- 撤销后新目录查询和文件读取失败关闭；既有 ResourceFS/rclone 缓存的失效时限仍遵守 ADR-0107 的后续约束。

## 验证

- Skill 包测试覆盖路径穿越、Unicode 隐形字符、大小写/前缀冲突、严格 Base64/UTF-8、摘要稳定性、大小与文件数；
- 领域与 API 测试覆盖角色矩阵、自审拒绝、幂等摘要、CAS、完整状态流、重复 Header、超限正文和安全错误信封；
- 持久化测试覆盖动态发布角色、RLS/ACL、对象条件写入与完整 GET 校验、数据库二次鉴权及发布/撤销目录事务；
- 进程测试覆盖 development 固定身份、production 独立 JWT/PG/S3/TLS 配置、继承环境拒绝与关闭顺序；
- 管理 Web 测试和实际浏览器走查覆盖队列、详情、上传与全部状态操作；
- 执行配置契约、格式、lint、受影响包 typecheck/test/build 和清理工作区全量 Gate。

## 可逆性与回退

发布前可关闭管理入口并执行 0032 down。存在 operator、申请、命令或审计事实时，down 必须失败关闭；应先保留表为
只读并导出审计，再制定显式迁移。已经公开的 Skill 版本属于生产目录事实，回退管理服务不能删除它；可先使用撤销
事务停止新读取，再移除应用。内容寻址对象在确认无任何目录/申请引用且超过保留期前不得删除。
