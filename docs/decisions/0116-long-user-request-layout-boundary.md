# ADR-0116：超长用户请求的对话布局边界

- 状态：已接受
- 日期：2026-08-06
- 决策者：Runtime 团队
- 关联问题：超长结构化用户请求会把消息气泡推离可视区域，页面只剩大块空白

## 背景

Thread 连续对话使用 CSS Grid 排列消息，单条消息本身是 Flex 容器。用户请求气泡使用右对齐和
`width: fit-content`。当请求包含数千字符的 JSON、工具 Schema 或其他长技术标识符时，消息行作为 Grid
子项会按最小内容宽度扩张。已在本地页面确认：一个 6487 字符的请求把消息行扩张到约 7135px，而气泡位于
可视区域右侧约 6459px 处，因此用户看到的只是与消息等高的大块空白。

消息内容本身没有丢失，问题属于布局溢出；不能通过截断或删除用户输入来规避。

## 决策驱动因素

- 用户输入必须完整保留并可阅读；
- 普通短消息仍应保持右对齐、内容自适应宽度的气泡样式；
- 修复应覆盖已持久化消息和发送中的本地消息；
- 不引入 JavaScript 文本测量、截断状态或新的运行时依赖。

## 备选方案

### 方案 A：截断超长用户请求并提供展开按钮

可以控制首屏高度，但改变了消息的默认可见性，需要新增展开状态和可访问性处理，也没有解决横向最小内容宽度的根因。

### 方案 B：为消息行建立可收缩边界，并允许用户气泡内部任意断行

给消息行设置 `width: 100%` 和 `min-width: 0`，阻止 Grid 子项按最小内容宽度撑开；同时给用户气泡设置
`overflow-wrap: anywhere`，使超长不可分词标识符在气泡内部换行。短消息仍由 `fit-content` 保持紧凑。

### 方案 C：仅给运行区域增加横向滚动

可以访问被推离的内容，但用户仍会先看到空白，还会引入不符合对话阅读习惯的数千像素横向滚动。

## 选择

选择方案 B。所有 `.message` 行固定占据可用正文宽度并允许收缩；用户请求气泡保留现有最大宽度和右对齐规则，
但其文本允许在任意必要位置断行。

## 理由

该方案直接修复 Grid 子项的固有尺寸传播，同时保留现有消息结构、完整文本和视觉语义。与截断相比没有交互状态，
与横向滚动相比能保证气泡始终位于当前视口内，且 CSS 改动可独立回退。

## 影响

### 正面影响

- 超长 JSON、工具 Schema、路径和连续技术标识符不再把用户气泡推离视口；
- 已持久化请求和待发送请求共享同一布局规则；
- 普通短消息的右对齐紧凑气泡不变。

### 负面影响与成本

- 不可分词的超长标识符可能在任意字符处换行；
- 极长请求仍会产生较高的纵向内容，需要使用既有运行区域滚动查看。

### 安全、数据与运维影响

- 不改变 API、持久化数据、权限或日志；
- 不截断、不复制用户内容，也不新增依赖和运维配置。

## 验证

- 样式契约测试确认消息行具备 `width: 100%`、`min-width: 0`，用户气泡具备 `overflow-wrap: anywhere`；
- Web 单元测试、类型检查、格式检查和 lint 通过；
- 在 785px 宽本地页面复查同一 6487 字符请求，消息行宽度不超过运行区域，气泡位于可视区域内且正文可见。

## 可逆性与回退

删除新增的三条 CSS 声明和对应测试即可回退；没有数据迁移或不可逆状态。若后续需要折叠超长请求，应作为独立交互决策新增实现。
