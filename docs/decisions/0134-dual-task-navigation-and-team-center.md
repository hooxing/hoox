# ADR-0134：个人与团队双任务导航及团队中心边界

## 状态

已接受（试验版）。

## 背景

ADR-0133 将客户端设计为单一活动 Tenant，并让团队切换器替换整个任务列表。试用后发现，这会把“查看哪个团队”和“当前对话属于哪个空间”混为一件事：切到团队后个人任务消失，左上角“新建会话”也容易被理解成团队会话；在侧栏内直接创建团队，还挤占了有限的任务导航空间。

产品需要固定展示个人任务，同时只展示一个已选团队的任务；团队任务区域必须限高，不能压缩掉个人任务。团队创建、加入和成员管理属于独立管理流程，不应嵌入任务树。

## 决策

### 双任务导航、单一执行空间

侧栏固定保留“个人任务”，并在默认折叠的团队区域中展示一个已选团队的任务。团队下拉只包含团队，不把“个人空间”伪装成团队选项，也不同时展开多个团队任务树。

双任务导航只是两个 Tenant 的只读投影；客户端真正执行请求时仍只有一个活动 Tenant。点击个人任务会切到个人 Tenant，点击团队任务会切到对应团队 Tenant。左上角“新建会话”始终切到个人 Tenant 并保持空会话；“新建团队对话”只存在于已选团队区域。

为避免通过可变的活动 Tenant 串行切换并产生竞态，任务列表读取增加显式 Tenant 参数。并行读取个人与团队任务时不改变当前活动 Tenant；创建 Run、上传文件等写操作仍服从当前活动 Tenant。

### 团队选择与当前对话解耦

客户端分别维护“当前对话所属团队”和“侧栏已选团队”。切换团队下拉只改变团队任务投影以及团队云盘的候选团队，不中断当前个人或团队对话。只有选择团队任务或新建团队对话时才改变活动 Tenant。

团队区域的任务列表限制最大高度并独立滚动，个人任务列表使用侧栏剩余空间。这样无论团队任务多少，个人任务入口都保持可见。

### 团队中心

创建团队、查看加入状态和进入成员管理统一放入“团队中心”弹窗。用户尚未加入任何团队时，点击团队入口直接打开团队中心并聚焦创建流程，不展开空任务栏。

当前试验版尚无邀请链接和待接受状态。“加入团队”沿用既有安全边界：Owner 或管理员按用户 ID 添加成员，用户随后刷新团队列表。界面明确说明该流程，不提供仅凭团队 ID 自助加入的越权入口。

## 影响

优点：个人任务保持稳定可见；团队切换不会打断当前对话；“新建会话”的个人语义明确；团队管理不再挤占任务树；显式 Tenant 读取消除了双列表加载时的请求竞态。

代价：客户端需要维护个人任务缓存、当前团队任务缓存以及活动 Tenant 三份相关状态；首屏会额外读取一次任务投影；邀请制加入仍需后续服务端模型才能形成完整闭环。

## 验证

- API 测试验证显式 Tenant 任务读取不修改活动 Tenant，个人请求不携带团队头。
- 组件测试验证团队下拉不含个人空间、无团队时直接打开团队中心、团队创建与加入说明不在侧栏内。
- 工作台测试验证个人与团队任务同时存在，选择团队任务会切换 Tenant，而左上角新建会话会回到个人 Tenant。
- 浏览器复验侧栏折叠、限高滚动、团队中心弹窗和两栏任务在实际视口中的布局。

## 可逆性

可删除显式 Tenant 的任务列表读取并恢复单列表导航；服务端数据模型和既有团队事实不受影响。团队中心仅重组现有创建、成员管理和刷新入口，不改变成员授权语义。
