# ADR-0143：上传资源名称规范化与幂等边界

- 状态：已接受（试验版）
- 日期：2026-08-10
- 决策者：Runtime 团队
- 关联任务/PR：`codex/team-edition-prototype`
- 关联决策：ADR-0003、ADR-0005、ADR-0016、ADR-0023、ADR-0077、ADR-0118、ADR-0139

## 背景

资源上传把文件名作为 Resource 与历史文件目录中的用户可见名称，同时也把上传请求内容纳入摘要和幂等边界。现有名称校验先以 Unicode
NFKC 计算规范形，再要求规范形与原始输入完全相同。因而兼容 Unicode 字符（例如全角括号）虽然可被无歧义地规范化，仍会被错误地拒绝为
400；用户上传的文件尚未进入 Blob、Resource 或 Thread 附件事实源。

文件名仍是安全边界：空名、控制字符、格式字符、Unicode 代理字符以及超过 UTF-8 255 字节的名称不能进入任何持久化目录或资源记录。
同时，相同逻辑名的兼容字符写法不得因摘要不同而绕过上传幂等语义。

## 决策驱动因素

- 兼容 Unicode 文件名应在不要求用户重命名的情况下稳定上传；
- 持久化名称、目录投影、请求摘要和幂等判断必须使用同一套名称语义；
- 不能放宽路径、控制字符或 Unicode 非标量值的拒绝边界；
- 不改变 Blob 内容、Tenant 授权、附件所有权或对象存储键的既有事实源；
- 已存在的资源名称与已记录的请求需保持可读、可下载和可审计。

## 备选方案

### 方案 A：继续要求原始名称已经是 NFKC

不采用。实现最简单，也不会改变现有摘要，但把正常操作系统和浏览器可能产生的兼容 Unicode 文件名变成 400，且用户难以理解应如何修正。

### 方案 B：接受兼容字符，但保留原始名称持久化

不采用。若校验、持久化、目录名和摘要分别使用原名或规范名，会让视觉相近名称出现重复、覆盖和幂等不一致；后续读取端也必须重做多套
比较规则。

### 方案 C：服务端统一规范化后持久化，并以规范名计算摘要

采用。服务端先对客户端提供的名称执行 Unicode NFKC 与 `trim`，随后以结果作为唯一的有效名称。空结果、控制字符、格式字符、代理字符、
UTF-8 编码长度超过 255 字节的结果继续拒绝。上传请求摘要和幂等键中使用该规范名，而非客户端原始写法。

## 决策

1. 所有资源上传入口在安全名称校验处先执行 Unicode NFKC，再执行 `trim`；所得值称为“规范名”。
2. 校验针对规范名执行：规范名为空、含控制类别字符（`Cc`）、格式类别字符（`Cf`）或 Unicode 代理字符，或其 UTF-8 字节长度超过
   255 时返回既有输入错误。ResourceFS 继续只使用其既有安全文件名投影，名称规范化不放宽 Workspace 路径规则。
3. Resource、版本、附件、历史目录条目以及向用户返回的文件名均持久化和投影规范名；不另外保存未规范化原名作为可执行路径或身份。
4. 请求摘要、幂等冲突检测和去重比较使用规范名。仅原始兼容字符写法不同、但规范名相同的两个请求，按同一上传语义处理。
5. Blob 内容、MIME 推断、文件大小、授权、对象存储键与上传事务边界不因名称规范化而改变。

## 理由

服务端规范化将用户体验问题收敛在唯一的输入边界，避免 Web、API、Worker、ResourceFS 和数据库各自解释 Unicode。把同一个规范名同时用于
持久化与摘要，保证名称比较与幂等结果一致；保留原有危险字符、长度和路径规则则不会把兼容性修复扩大为路径解析放宽。

## 影响

### 正面影响

- 含全角括号等兼容 Unicode 的正常文件名可直接上传；
- 用户可见名称、ResourceFS 路径和 API 返回值保持一致；
- 兼容等价写法不会创建摘要不同的重复上传或绕过幂等判断；
- 规范化只影响名称，文件字节与已有所有权边界不变。

### 负面影响与成本

- 上传成功后展示的名称可能与客户端选取时的字面原名不同；
- 两个原名不同但 NFKC 后相同的并发上传会进入相同幂等/冲突语义，调用方不能依赖原始字形区分它们；
- 需要保证所有上传入口都复用同一名称规范化函数，不能在客户端自行替代服务端校验。

### 安全、数据与运维影响

- 继续拒绝控制、格式和代理字符，避免不可见字符、双向格式控制与非标量 Unicode 进入目录和日志；
- UTF-8 长度上限仍由规范名计算，避免规范化后长度边界在存储与文件系统间不一致；
- 不记录原始名称可减少同一资源存在两套可被误用的路径身份；如需审计客户端原文，应另行定义脱敏、访问控制与保留期，不能把它并入资源名；
- 既存持久化名称不做批量重写，避免目录路径和历史引用发生无必要变动。

## 验证

- 上传服务测试覆盖全角括号被规范化，并证明 Resource 返回名称与 `/resources` 路径使用同一规范名；
- 名称拒绝测试覆盖空白名、格式字符、代理字符和超过 255 字节的名称，且失败发生在 Blob 持久化之前；
- 幂等测试覆盖全角与半角括号两种 NFKC 等价原名产生相同请求摘要；
- 受影响 Resource 包执行格式、Lint、TypeScript 与直接覆盖修改的测试；
- 本地 API 重新构建后，以原失败文件名联调上传，响应应返回规范名而不再返回 400。

## 可逆性与回退

代码可回退到旧校验逻辑，但在回退窗口内已经以规范名持久化的资源不会被删除或改名，仍按已存名称读取。回退后新的兼容 Unicode 上传会再次
被拒绝，而已成功上传的文件保持可读。由于请求摘要是事实的一部分，不能通过重写历史摘要来“恢复”原始字形；若未来需要保留原名或改用其他
规范化算法，应新增替代 ADR，并设计显式的数据迁移与幂等兼容策略。

## 后续工作

- 将名称规范化收敛为共享边界函数，并禁止各上传调用方各自实现；
- 在 API 与前端显示中明确使用服务端返回的规范名；
- 监测规范化导致的幂等复用和冲突数量，确认没有异常客户端持续发送不可见字符。
