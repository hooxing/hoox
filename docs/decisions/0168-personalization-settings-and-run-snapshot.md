# ADR-0168：个人与团队个性化使用 Run 级低信任偏好快照

- 状态：已接受
- 日期：2026-08-12
- 决策者：Runtime 团队与产品负责人
- 关联：细化 ADR-0029 的可信 Prompt 分层、ADR-0140 的个人/团队入口和 ADR-0147 的团队管理权限

## 背景

产品需要允许用户保存一段长期个性化内容，并在之后的任务中自动提供给模型。个人任务携带个人个性化；团队任务默认同时携带当前发起用户的个人个性化和当前团队个性化。用户加入至少一个团队后，可以关闭“应用于团队任务”；团队 Owner 或管理员可以修改团队个性化，普通成员只读。

用户还确认：个性化是可以被当前任务覆盖的偏好；老对话中的下一次新任务使用保存后的最新配置；个人入口位于侧边栏独立位置，团队入口位于团队设置。

现有架构要求 system/developer prompt 在相同能力配置下保持字节稳定，用户、团队等请求级动态内容不得进入可信 system prompt。把配置正文直接拼入 system prompt 会破坏上下文缓存，并把可编辑内容提升为平台指令。因此需要在“长期可见”和“可信 Prompt 稳定”之间建立明确边界。

## 备选方案

### 方案 A：把个人和团队正文直接拼入 system prompt

实现最直接，也能获得较高指令优先级，但会违反稳定 Prompt 不变量；任一用户或团队修改都会改变 system prompt、恢复兼容身份和缓存前缀，并使越权文本更接近平台规则，拒绝。

### 方案 B：每次由 Web 把个性化正文附加到任务请求

不需要 Worker 查询，但客户端可以伪造团队正文，离线重试可能携带旧版本，API、Web 和其他入口也容易产生行为漂移，拒绝。

### 方案 C：服务端持久化，Worker 领取 Run 后读取一次并作为专用 user/custom 上下文注入

system prompt 只增加字节稳定的解释规则；动态正文使用 `runtime.personalization_context.v1`。Worker 从 Run 已有的发起用户快照确定个人身份，在当前 Tenant 授权下读取配置，并将不可变快照同时交给 Root 和子 Agent。

## 决策

采用方案 C，并确定以下语义：

1. 个人和团队设置分别存入 `user_personalization_settings` 与 `team_personalization_settings`；无记录等价于空正文、个人团队开关默认开启、版本为 0。
2. 个人内容仅本人读写。团队内容所有活跃成员可读，仅 Owner/Admin 可写；团队写入继续使用独立 Team Coordinator 数据库角色，普通 Runtime 只有团队表读取权限。
3. 每个更新使用 `expectedVersion` 做乐观并发控制。保存成功后版本递增；冲突返回 409，不做最后写入者静默覆盖。
4. 新 Run 被 Worker 领取后读取当时的最新配置并形成内存快照。正在运行的 Run 不受后续修改影响；老对话之后创建或激活的新 Run 使用新配置。Root 与所有子 Agent 共用同一快照。
5. 个人任务只携带个人个性化。团队任务始终携带非空团队个性化，并在个人开关开启时携带当前 Run 发起用户的非空个人个性化。该开关默认开启，只在用户至少加入一个团队后显示。
6. 模型可见顺序固定为团队个性化、个人个性化、其他 Tenant 上下文、Skill 上下文、User 上下文；具体 Skill 指令在这些长期偏好之后加载。冲突优先级为平台规则高于当前请求和 Skill，当前请求和 Skill 可覆盖长期偏好，团队偏好冲突时高于个人偏好。
7. 正文不进入 system prompt、工具 Schema、日志、指标或错误正文。system prompt 只包含固定的偏好解释与优先级规则。
8. 每个作用域最多 2,000 个 Unicode code point 且最多 8 KiB UTF-8。输入统一 LF、去除外层空白并规范化为 NFC；拒绝控制字符、Bidi、零宽和异常变体选择符；空白正文表示关闭。所有边界明确拒绝超限，不静默截断。

## 影响

- 个人和团队任务可以稳定复用长期偏好，同时保留 system prompt 缓存前缀和平台指令边界。
- 团队同一对话可以由不同成员继续发起任务；个人个性化按每个 Run 的实际发起用户选择，不错误沿用 Thread 创建者。
- 配置修改与排队任务激活之间以 Worker 领取时间为快照点。极端长队列会使用激活时而不是提交时的最新配置，这是“新任务使用新配置”的明确取舍。
- Prompt 版本从 v9 升级到 v10，因为稳定 Harness 新增了个性化上下文解释；动态正文自身不进入恢复兼容策略摘要。
- 新增两张 RLS 表、API GET/PUT 契约、Web 弹窗和团队设置区；生产迁移使用 0046。
- 个人弹窗中的团队应用开关保留原生 checkbox 语义与整行点击区域，视觉上使用带明确开/关状态的滑动开关；这只改变交互呈现，不改变默认开启和保存契约。

## 安全与隐私

- UI 说明团队开关的效果，但不默认把个人正文展示给团队成员。团队成员只能查看团队正文。
- 模型可能在团队输出中体现已启用的个人偏好，因此用户可以在加入团队后关闭团队应用；默认开启是产品选择，而不是权限授权。
- Team Coordinator 相对 Runtime 额外增加团队个性化表的 INSERT 和受限列 UPDATE；Worker 与普通 API Runtime 不能修改团队设置。
- 数据库 RLS、Membership 状态和角色共同复核访问，客户端提交的 Team ID 仅作选择器。

## 验证

- 领域测试覆盖 NFC/LF、双长度上限和不可见字符拒绝。
- 迁移与 Repository 测试覆盖 RLS 文本、ACL 边界、默认开启、团队任务双内容、关闭后的团队单内容和个人任务不受开关影响。
- Prompt 测试覆盖团队在个人之前、二者在 Skill 动态上下文之前、正文不进入 system prompt。
- Worker 测试覆盖按 Run 发起用户读取一次，并将同一快照交给 Session。
- API 测试覆盖个人/团队作用域、内容规范化、版本冲突和团队可编辑投影。
- Web 测试覆盖个人入口请求作用域、加入团队后显示默认开启开关、无团队时隐藏开关以及团队设置读写。

## 可逆性

在两张设置表没有数据时，可以执行 0046 down 并回退 API、Worker 和 Web。只要任一表存在用户数据，down 会拒绝破坏性回滚；需要先导出并经产品明确授权删除数据。关闭 Worker 注入可以临时停止模型使用个性化，但不能把已有版本事实伪装为未创建。Prompt v10 回退到 v9 会改变恢复兼容身份，只能在停止新 Run 并确认恢复策略后进行。
