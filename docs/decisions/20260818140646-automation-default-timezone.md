# ADR-20260818140646：对话定时任务默认使用东八区

- 状态：已采纳
- 日期：2026-08-18
- 决策者：项目维护者
- 关联任务/PR：定时任务时区默认值修正
- 替代关系：无

## 背景

`automation_update` 创建定时任务时同时接收带时区偏移的 ISO 8601 首次执行时间和 IANA 时区。此前创建参数强制要求模型显式填写 `timezone`，但工具契约没有声明用户未指定时区时应采用什么默认值，容易出现模型选择 UTC、首个执行时间按东八区理解、任务元数据却记录另一时区的错配。

当前产品的主要用户和运行环境以中国标准时间为默认语境，仓库中的历史目录时间也默认使用 `Asia/Shanghai`。

## 决策驱动因素

- 用户未明确说明时区时，定时任务应有稳定、可预期的时间语义；
- 工具 schema、模型说明与持久化数据必须使用同一个默认值；
- 用户明确指定其他时区时不能被默认值覆盖；
- 默认规则不应依赖 Worker 宿主机的本地时区。

## 备选方案

### 方案 A：继续强制模型每次填写时区

不改变现有接口，但默认语义仍然隐含在模型推理中，容易产生 UTC 与用户本地时间错配。

### 方案 B：从用户或浏览器设置推导时区

个性化程度更高，但当前 Worker 的工具执行上下文没有可靠、统一的用户时区设置，贸然推导会引入新的动态上下文和兼容边界。

### 方案 C：工具创建请求默认使用 Asia/Shanghai

允许创建参数省略 `timezone`，在工具参数转换边界写入稳定的 `Asia/Shanghai`；显式时区保持原值。

## 选择

选择方案 C。导出共享常量 `DEFAULT_AUTOMATION_TIME_ZONE = "Asia/Shanghai"`，`automation_update` 的 create schema 将 `timezone` 改为可选，并在转换为领域命令时补齐该默认值。工具说明同时要求：未指定时区时，`first_run_at` 应按 UTC+08:00 换算并携带 `+08:00` 偏移。

更新操作仍保持现有语义：省略 `timezone` 表示不修改任务已有时区。用户显式指定其他合法 IANA 时区时保留其选择。

## 理由

该方案在不依赖宿主机环境、不增加请求级动态提示的情况下消除了缺省歧义，并且只改变对话工具的创建边界，不修改已有任务和 API 的兼容语义。

## 影响

### 正面影响

- 用户未指定时区时，创建结果稳定为东八区；
- 工具 schema 明确默认值和首次执行时间的偏移要求；
- 显式指定海外时区的任务不受影响。

### 负面影响与成本

- 非东八区用户若不主动说明时区，也会得到东八区任务；
- 后续引入用户级时区偏好时，需要定义其优先级和迁移方式。

### 安全、数据与运维影响

- 不新增数据表或迁移；
- 不读取 Worker 宿主机时区；
- 已存在任务不会被批量改写。

## 验证

- 契约测试验证 create schema 接受省略 `timezone`；
- 单元测试验证省略时转换为 `Asia/Shanghai`；
- 单元测试验证显式 `America/New_York` 不被覆盖；
- 执行 automation 与 pi-adapter 的测试、类型检查、lint 和格式检查。

## 可逆性与回退

恢复 create schema 中 `timezone` 的必填约束并删除转换默认值即可回退。由于持久化层始终存储显式时区，回退不需要数据库迁移，已创建任务继续保留 `Asia/Shanghai`。

## 后续工作

- 若产品增加用户级时区设置，另行决策“用户设置 > 显式工具参数 > 系统默认”的优先级。
