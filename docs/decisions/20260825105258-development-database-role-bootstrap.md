# ADR-20260825105258：开发数据库角色可重复补齐与精确诊断

- 状态：已接受
- 日期：2026-08-25
- 决策者：Runtime 团队
- 关联任务/PR：消除多开发机角色契约演进导致的重复启动阻塞
- 替代关系：补充 [ADR-0154（集群级数据库角色）](0154-cluster-scoped-database-roles-and-development-env-source.md)，不改变数据库专属角色和生产运维边界

## 背景

PostgreSQL 登录角色属于集群而不是单个数据库，业务 migration 不能可靠创建这些角色。两台开发机可以同步代码和 Schema migration，却仍分别缺少后来新增的 Admin Control 等集群级角色。现有 migration preflight 把“角色不存在”和“角色被其他数据库依赖”收敛为同一句跨库复用错误，导致维护者反复排查错误方向，并临时绕过完整 API。

仓库已有 `DATABASE_BOOTSTRAP_URL` 和六个应用角色连接，但没有日常可重复执行的角色补齐入口。要求每次角色契约变化都手工复制 SQL，无法保证两台开发机同步执行，也容易误改既有角色密码或授权。

## 备选方案

### 方案 A：继续由维护者手工创建缺失角色

不增加代码，但错误会随角色集合演进重复出现，操作不可发现、不可测试，也无法在两台机器上稳定复现。

### 方案 B：让 migration 自动使用 Database Admin 创建角色

操作最少，但会把集群级管理员凭据带入普通迁移入口，混淆角色准备与业务 DDL 边界，并扩大生产误用风险。

### 方案 C：增加显式、可重复的本地角色补齐命令并拆分诊断

保留 Database Admin 与 Migrator 分离。独立命令只创建缺失角色；migration 继续只验证角色、Schema 与 ACL。角色缺失和真实跨库复用分别报告可操作信息。

## 选择

采用方案 C：

1. 新增 `pnpm db:roles:bootstrap`，从本机 `.env` 的六个应用连接提取各自角色密码，并使用 `DATABASE_BOOTSTRAP_URL` 补齐缺失登录角色；
2. 新增 `pnpm db:setup`，按“角色补齐 → 向上迁移”顺序执行，作为开发机同步数据库契约的日常入口；
3. 补齐命令只允许非 production 环境，并要求 Database Admin 同时拥有当前数据库和角色管理能力；
4. 六个应用 URL 必须与 bootstrap URL 指向同一数据库，URL 用户名必须等于对应角色变量，六个角色必须互异；
5. 补齐过程使用数据库级事务 advisory lock，先拒绝任何跨数据库依赖，再只创建缺失角色并授予当前数据库 `CONNECT`；
6. 已存在角色的密码、属性、成员关系和 ownership 不由该命令隐式修改；首次数据库、Schema 与默认权限准备仍由 Database Admin 按维护者文档执行；
7. `db:roles:bootstrap` 与 `db:migrate:*` 在进程内读取仓库根 `.env`，文件值覆盖长驻终端继承的同名变量，避免两个步骤操作不同数据库；
8. migration preflight 将角色缺失、跨库复用和目录查询异常拆成不同错误，且不输出连接串或密码。

## 理由

独立补齐命令消除了“代码已同步、集群角色未同步”的人工缺口，同时不让普通 migration 获得管理员能力。只创建缺失角色使重复执行保持幂等，也避免第二台机器意外轮换已存在角色的密码。URL 与角色交叉校验可在连接数据库前发现 `.env` 串库或用户名漂移；数据库命令主动让 `.env` 覆盖继承环境，避免长驻终端旧值让补齐和迁移落到不同数据库；`pg_shdepend` 仍是跨数据库依赖的事实源。

## 影响

### 正面影响

- 新增应用角色后，两台开发机都可以运行同一命令补齐本机 PostgreSQL 集群；
- 缺少角色会直接报告角色名和修复命令，不再伪装成跨库复用；
- 真实跨库复用会报告具体角色和数据库，缩短隔离排查；
- Database Admin 凭据仍不进入 API、Worker、Scheduler 或普通 migration 连接。

### 负面影响与成本

- 本机六个应用 URL 必须包含可用于首次创建角色的密码，并与角色变量、数据库目标保持一致；
- 既有角色密码或属性错误仍需显式运维处理，补齐命令不会静默修正未知状态；
- 全新数据库仍需先完成数据库、Schema、`PUBLIC` 权限和 ownership 的一次性准备。

### 安全、数据与兼容影响

命令不修改业务数据，不删除角色，不转移 ownership，也不接触其他数据库对象。跨库依赖在任何 `CREATE ROLE` 前失败关闭。日志只包含稳定错误、角色名和数据库名，不包含 URL、密码或驱动 cause。production 明确拒绝执行该本地命令。

## 验证

- 单元测试覆盖缺失角色的单独创建、`CONNECT` 授权、密码 SQL 转义和重复角色校验；
- 单元测试覆盖 Database Admin 权限不足及跨数据库依赖时零创建；
- 配置测试覆盖六个 URL 的数据库一致性、用户名与角色一致性、默认端口归一化和 production 拒绝；
- 环境加载测试覆盖仓库 `.env` 覆盖继承旧值以及文件缺失时保留显式注入；
- 角色作用域测试分别覆盖通过、缺失、跨库复用和查询结果不完整诊断；
- persistence typecheck、目标 Vitest、格式、lint 和 diff 检查作为提交前验证。

## 可逆性与回退

可以删除两个开发命令并恢复旧诊断，不需要回滚数据库数据。命令已创建的登录角色属于显式本地运维结果，回退代码不会自动删除；如需删除，必须先确认没有任何数据库依赖并由 Database Admin 单独处理。
