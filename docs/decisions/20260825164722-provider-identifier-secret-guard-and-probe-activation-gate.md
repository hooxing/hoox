# Provider 内部标识防密钥误填与探测后启用门禁

- 状态：已接受
- 日期：2026-08-25
- 决策者：Runtime 维护者
- 关联任务/PR：修正后台 Provider 配置泄密风险与模型生效语义
- 替代关系：细化 ADR-20260819165254 与 ADR-20260820090402 的秘密边界和启用前置条件，不改变 Run 快照语义

## 背景

部署测试中发现，管理员可能把 Provider API Key 误填进 `providerKey`。该字段原本按普通内部标识保存，因而会进入
revision、对象键和追加式审计，并在管理页面回显。虽然真正调用模型的密钥仍只由 `MODEL_API_KEY` 注入，页面也不会
读取部署秘密，但“页面不保存密钥”的说明无法防止操作人员把密钥写入非秘密字段。

同一测试还暴露出两个生效语义问题：Provider 探测失败或尚未探测时仍可请求发布；模型页面也没有把待发布 revision、
当前 active revision 和无 active 时的部署回退区分开。结果是管理员看到“草稿已保存”，却容易误以为实际模型已经
切换。

## 决策驱动因素

- 任何可回显、可审计的普通标识字段都不能成为秘密材料的替代存储；
- 启用门禁必须位于领域服务，不能只依赖按钮禁用；
- 页面必须直接回答“当前实际使用哪个模型”，并说明对已有 Run 与新 Run 的不同影响；
- 历史追加式 revision 和审计不能通过修改迁移或原地改写来伪造未发生过的事实；
- 后台不可用时仍应保留 Pi 公开目录浏览，但不能把本地表单误称为已保存或已生效配置。

## 备选方案

### 方案 A：只修改页面文案

实现成本最低，但 API 调用方仍可写入疑似密钥并绕过探测门禁，不能建立安全不变量，故不采用。

### 方案 B：把 Provider 密钥改为后台可编辑字段

可以让标识和密钥在界面上更易区分，但会把浏览器、数据库、审计和控制 API 扩展为秘密管理系统，违反现有部署秘密
边界，故不采用。

### 方案 C：领域拒绝、页面拦截与历史隔离同时实施

领域入口拒绝常见 API Key 形态的 Provider 内部标识；页面在录入时清空疑似密钥，并对历史异常标识统一遮蔽、禁用
编辑和操作。Provider revision 只有探测状态为 `healthy` 时才允许启用。页面独立展示 active/fallback/unknown 状态。

## 选择

采用方案 C，并固定以下边界：

1. `providerKey` 是小写的平台内部稳定标识，只用于版本、路由和审计，不是 API Key 输入框。模型与记忆配置在领域
   规范化入口拒绝常见 `sk-`、`rk-`、`pk-`、GitHub、Slack 与 Hugging Face Token 形态；管理页面在录入时立即清空
   同类内容并提示轮换。
2. 已存在的可疑 revision 和审计保持原始追加式事实，不修改已执行迁移，也不自动重写数据库。控制服务在列表、概览
   和审计读取投影中只返回固定脱敏占位符；管理页面所有可见和可访问性文本统一显示“疑似密钥（已隐藏）”，并禁止
   继续编辑、探测或启用。运维人员必须在对应 Provider 侧轮换暴露过的密钥，再创建使用正常内部标识的新配置。
3. 模型与记忆 Provider revision 只有持久化探测状态为 `healthy` 时才允许启用。该校验由 `admin-control` 领域服务在
   调用 repository 发布前执行；运行参数 revision 不要求外部连接探测。
4. 模型页面优先展示当前生效事实：有 active revision 时显示 Provider、默认模型、revision 与 generation；无 active
   revision 时明确显示继续使用部署环境 `MODEL_BASE_URL`、`MODEL_ID` 和 `MODEL_API_KEY`；控制服务不可用时只显示
   “状态未知”。页面只显示部署密钥是否配置，永不显示值。
5. active 切换只影响启用后首次建立配置快照的新 Run。已有 Run 继续使用 `run_runtime_config_snapshots` 中的不可变
   revision；待启用配置、探测结果和 Pi 目录选择都不改变实际调用。
6. 继续保留浏览器内置 Pi 目录的独立降级。后台不可用时允许浏览和编辑初始值，但页面必须明确这些内容尚未保存、
   尚未探测且尚未生效。
7. 首版仍只有部署级 `MODEL_API_KEY`，不会为每个 Provider 保存独立密钥。切换到需要其他凭据的 Provider 前，必须先
   通过部署系统更新该秘密；Provider revision 只管理非秘密调用参数。

## 理由

领域拒绝保证所有入口共享同一安全下限，页面拦截减少误操作，历史隔离则在不破坏不可变审计的前提下停止继续传播。
探测后启用把“连接可用”从建议步骤提升为真正状态机门禁。独立生效状态卡把配置编辑和运行事实分开，管理员无需从
revision 列表推断当前模型。

## 影响

- 新建模型和记忆配置会拒绝疑似 API Key 的内部标识；合法但恰好命中启发式规则的标识需要改用普通平台别名；
- 历史疑似密钥不会因这次代码变更从数据库消失，必须视为已暴露并执行轮换；
- 探测失败或尚未探测的 Provider 无法启用，恢复路径是修正地址、部署秘密或白名单后重新探测；
- 页面术语从泛化的“发布草稿”收敛为“保存待启用配置—探测连接—启用配置”，底层不可变 revision 与审计模型不变；
- 无 active revision 或控制服务故障时，页面不再暗示 Pi 目录或待启用配置已经影响 Worker。

## 验证

- `admin-control` 领域测试覆盖疑似密钥拒绝、读取投影脱敏、失败探测阻断启用和健康探测放行；
- `admin-web` 测试覆盖部署回退状态、部署密钥只显示状态、失败探测按钮禁用、健康版本启用、历史可疑标识全量遮蔽
  以及输入时清空；
- 离线控制台测试继续覆盖后台不可用时可浏览 Pi Provider 和打开编辑表单，同时展示实际模型状态未知；
- 受影响包继续执行格式、lint、typecheck 和测试，浏览器人工验收模型页面的桌面布局与交互。

## 可逆性与回退

页面状态卡、文案和输入拦截可以独立回退，不涉及数据迁移。领域探测门禁若因紧急兼容需要回退，可恢复原发布路径，
但会重新允许未经验证的 Provider 生效，应作为显式安全降级记录。历史数据保持不变；任何已经轮换的外部密钥不得恢复。
