# 模型配置保存即启用并隐藏内部版本流程

- 状态：已接受
- 日期：2026-08-25
- 决策者：Runtime 维护者
- 关联任务/PR：收敛后台模型配置为可直接使用的操作流程
- 替代关系：部分替代 ADR-20260819165254 的模型 Provider 草稿、原因和发布流程，替代 ADR-20260825164722 与 ADR-20260825173500 的模型 Provider 探测后启用门禁；记忆 Provider、Skill 发布、凭据加密和 Run 快照语义不变

## 背景

模型页面原本把控制面的内部状态机直接呈现给管理员：保存草稿后还要填写探测原因、执行连接探测、再次填写原因并启用，
同时展示同一 Provider 的多条 Revision 记录。管理员的实际目标只是填写 Provider 地址、API Key 和模型，然后立即让新 Run
使用该配置。草稿、探测记录、Revision 与变更原因没有帮助完成这个目标，反而让“已经填完”和“已经生效”成为两个容易
混淆的状态。

不可变 Revision 和 Run 配置快照仍然解决正在执行的 Run 不漂移、进程重启后可恢复的问题；Provider 密钥按 Revision
加密托管也已实际接入 Worker。这些内部机制不要求成为日常配置界面中的操作步骤。

## 决策驱动因素

- 管理员填写完模型连接和默认模型后，应通过一次明确操作完成保存与生效；
- 页面应直接回答当前使用什么配置，而不是要求管理员从版本记录推导 active 状态；
- 当前阶段优先保证模型切换可用，连接验证不作为生效前置门禁；
- 已开始 Run 的配置稳定性和托管密钥的可用性不能因简化页面而退化；
- 记忆 Provider 和 Skill 发布有不同的失败与治理边界，不随模型页面一起改动。

## 备选方案

### 方案 A：保留三步流程，仅优化文案

继续暴露“保存待启用配置—探测—启用”和 Revision 列表，能保留原有门禁，但管理员仍需理解内部状态机，不能解决配置
完成后未实际生效的问题，故不采用。

### 方案 B：保存前自动探测，成功后自动启用

页面可以减少按钮数量，但 Provider 的 `/models` 支持、网络波动或兼容网关差异仍会阻止配置生效；失败后还需要解释隐藏
的探测阶段。当前目标是先让管理员能够切换模型，故不把探测保留为同步门禁。

### 方案 C：一次保存并启用，Revision 仅作内部快照

模型页面以当前配置为中心。管理员点击“保存并使用”后，控制面保存不可变 Revision 并切换 active；页面不展示草稿、
Revision 历史、探测操作或变更原因。Worker 继续从 Run 快照读取准确 Revision 和对应托管密钥。

## 选择

采用方案 C，并固定以下边界：

1. 模型页面只提供当前 Provider 配置和“保存并使用”操作，不展示草稿、版本记录、独立探测按钮或变更原因输入。
2. 保存成功即切换模型 Provider 的 active Revision 并递增全局 generation，不再要求该 Revision 预先具有 `healthy`
   探测状态。控制面内部仍可使用固定原因写入既有审计协议，但不要求管理员填写。
3. 不可变 Revision 继续作为持久化和 Run 快照实现细节。页面显示当前 Provider、默认模型以及“只影响新 Run”的生效
   边界，不要求管理员通过 Revision 编号理解当前状态。
4. Worker 首次处理 Run 时仍将 active 模型 Revision 固化到 `run_runtime_config_snapshots`；已有 Run 的重试和恢复继续
   使用原 Revision、模型元数据与密钥，新保存的配置只影响之后首次建立快照的 Run。
5. 模型 API Key 仍是写入型字段，并继续按 ADR-20260825173500 加密后绑定 Revision。页面、读取 API、审计和错误响应
   不返回明文或密文；简化操作不回退已经存在的密钥托管能力。
6. Pi 目录继续提供内置 Provider 的模型元数据和默认模型选项，自定义 Provider 只要求手工填写必要连接与模型字段；
   保存后以显式配置为准。后台不可用时可以浏览目录和编辑表单，但不能声称保存或生效成功。
7. 记忆 Provider 仍保留待启用配置、连接探测和 admin 启用门禁；Skill 的提交、复核和发布流程也保持不变。

## 理由

一次保存直接对应管理员的目标，并消除“草稿已保存但模型未切换”的主要误解。Revision、generation、审计和 Run 快照
仍在服务端承担恢复与稳定执行职责，但不再把实现机制转换成用户必须操作的流程。取消模型探测门禁意味着错误地址或密钥
可能在新 Run 中暴露为调用失败；当前阶段接受这一取舍，管理员可修正配置并再次保存。

## 影响

- 模型切换从多步状态流收敛为一次“保存并使用”；
- 模型页面不再承担 Revision 历史、探测记录或人工原因录入界面；
- 保存错误配置可能导致之后的新 Run 调用失败，恢复方式是修正同一 Provider 配置并再次保存；
- 数据库中的历史 Revision、探测结果和审计事实不删除、不改写，也不需要迁移；
- Run 快照、generation、托管密钥加密和部署配置回退保持兼容；
- 记忆配置与 Skill 发布继续使用各自原有治理流程。

## 验证

- `admin-control` 领域测试证明模型 Revision 未探测也可启用，同时记忆 Provider 的探测门禁仍然生效；
- `admin-web` 测试证明模型页面不出现草稿、版本、探测和原因控件，保存会创建配置并立即切换 active；
- Worker 既有测试继续证明新 Run 读取 active Revision，已有 Run 固定原 Revision 和对应密钥；
- 受影响包执行格式、lint、typecheck 和定向测试，并在本地模型页面验证保存后的当前配置状态。

## 可逆性与回退

界面可恢复显式探测和版本操作；领域层也可重新增加模型探测门禁，不需要修改已有 Revision 或 Run 快照。回退前应确认
当前 active 配置已经探测健康，否则恢复门禁后再次发布会被拒绝。任何回退都不得删除历史配置或把已经托管的模型密钥
重新改为明文或普通配置字段。
