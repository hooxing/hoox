# 模型页面只启用所选模型，已发布能力驱动运行

- 状态：已接受
- 日期：2026-08-26
- 决策者：Runtime 维护者
- 关联任务/PR：修复模型配置生效后在调用前被本地能力断言中断
- 替代关系：部分替代 ADR-0138 对 `deepseek-v4-flash` 上下文窗口、最大输出和图片能力的固定值及阻断性装配校验；其模型 ID、thinking、Chat Completions 兼容项与 payload 规范化继续有效。部分替代 ADR-20260820090402 在管理页面同时启用多个模型的选择；统一模型编辑与真实测试由 ADR-20260826115031 继续细化，多模型数据结构、显式默认模型和 Runtime 兼容能力继续有效

## 背景

模型控制面允许管理员从锁定版本的 Pi Provider 目录载入模型，也允许显式修改能力字段并保存为不可变 Revision。Worker
首次处理 Run 时会固定该 Revision，随后把其中的启用模型注册到 Pi，并使用显式默认模型。

ADR-0138 还在 Worker 中维护了第二份 `deepseek-v4-flash` 能力事实：上下文窗口、最大输出和图片能力必须与当时的
Oh My Pi Profile 常量完全相等。当前锁定 Pi 目录给出的同一模型能力已经不同。动态 Provider 装配会检查全部启用模型，
因此一个未被选为默认值的目录模型也能在任何网络请求之前阻断整个 Provider；用户选择的模型、地址和密钥均未获得调用
机会，Run 只能显示泛化的内部错误。

这不是外部输入的信任边界。模型 Revision 已经过领域结构校验，严格相等断言只是在同一进程内要求两份受维护数据保持
同步，既不能验证上游真实能力，也使后台配置失去实际控制权。

模型页面已经把内置 Provider 收敛成一个“使用模型”单选框，但提交时仍把目录中的每个模型强制保存为启用。用户无法看到
或关闭这些旁路模型，Runtime 也没有按 Run 从启用集合另选模型的消费者。这使旧的多启用扩展点变成隐藏状态，并直接扩大
了上述错误断言的影响范围。

## 决策驱动因素

- 已发布 Revision 必须是 Worker 使用的模型能力与预算事实，不能被隐藏的旧常量否决；
- 模型请求协议与模型容量是不同事实，不能因为需要 DeepSeek 协议兼容就固定所有能力数值；
- 非默认模型不能因无关的本地相等检查阻止默认模型创建 Session；
- 单选页面的保存结果必须与用户选择一致，不能暗中启用未选择模型；
- 必须继续保留模型目录的结构约束、默认模型约束、Run 快照和 DeepSeek 工具调用重放兼容；
- 当前阶段优先让显式配置能够形成真实请求，不增加新的探测、草稿或兼容状态机。

## 备选方案

### 方案 A：把 Pi 目录覆盖成 ADR-0138 的固定能力

可以让现有断言通过，但管理页面、生成目录和 Worker Profile 仍需同步维护同一组数值。上游或锁定 Pi 版本再次变化时会
重复故障，且页面展示值不再直接来自其声明的目录事实，故不采用。

### 方案 B：只校验默认模型

可以绕过本次旁路模型阻断，但管理员把 `deepseek-v4-flash` 选为默认模型时仍会因两份能力事实不同而失败。它减少触发
范围，没有消除重复真相，故不采用。

### 方案 C：Revision 拥有能力，Profile 只拥有协议

删除 DeepSeek 上下文、输出和图片能力的硬编码相等断言。精确模型 ID 仍选择 DeepSeek thinking、参数名和工具调用重放
协议；`input`、`contextWindow` 与 `maxTokens` 直接使用已发布 Revision。选择本方案。

## 选择

1. Worker 注册启用模型时不再要求 `deepseek-v4-flash` 的能力值等于本地固定常量。
2. `deepseek-v4-flash` 继续使用 high thinking、`max_tokens`、DeepSeek thinking 格式、禁用 developer role/store/
   reasoning effort，以及既有 payload 规范化；本次不删除协议兼容能力。
3. 模型的输入模态、上下文窗口和最大输出以 Run 固定的 Provider Revision 为准。领域层继续保证模型 ID 唯一、至少一个
   模型启用、默认模型指向启用模型、输入能力非空以及预算关系合法。
4. Worker 继续注册 Revision 中的全部启用模型并执行显式默认模型；不增加目录重写、自动探测或隐式回退。
5. 上游是否接受模型 ID、图片或预算参数由真实模型请求验证。调用失败沿既有 Provider 失败语义返回，不在 Session 创建前
   用旧能力常量猜测上游状态。
6. 管理页面从内置 Pi Provider 目录保存配置时，只把“使用模型”当前选择标记为启用；其他目录条目继续保存在 Revision
   中但标记为停用，便于再次编辑时切换。自定义 Provider 继续保留已有启用集合，并保证新选中的默认模型已启用。
7. 多模型协议和数据库形状继续兼容已有 Revision；本次不增加启用开关、模型路由策略或数据迁移。

## 理由

模型 Profile 的必要职责是补足通用 OpenAI-compatible 元数据无法表达的请求协议，而不是与管理配置竞争模型容量所有权。
把能力事实收敛到不可变 Revision 后，页面展示、Run 快照和 Worker 注册使用同一份数据；删除相等断言也不会削弱认证、
授权、凭据保护、结构校验或持久化边界。

## 影响

- 从 Pi 目录载入或显式编辑的 DeepSeek 能力值可以实际进入 Worker；
- 非默认的 `deepseek-v4-flash` 不再阻断其他默认模型的 Session 创建；
- 内置 Provider 页面保存后只有所选默认模型处于启用状态，页面选择与运行语义一致；
- 配置错误不再由本地旧常量提前发现，可能在真实 Provider 请求中暴露；这与模型配置保存即启用的既有取舍一致；
- DeepSeek 官方请求兼容和工具调用重放行为保持不变；
- 不修改数据库结构、历史 Revision、Run 快照或管理 API。

## 验证

- Worker 装配测试使用当前 Pi 目录的 `deepseek-v4-flash` 能力，并与一个不同的默认模型同时启用，证明 Provider 可创建且
  默认模型选择正确；
- 测试继续证明 `deepseek-v4-flash` 获得 DeepSeek 专用 compat，而其容量与输入模态保持 Revision 值；
- Pi Adapter 测试继续覆盖 thinking、Chat Completions 兼容项和 payload 规范化；
- 管理 Web 测试选择第二个 Pi 模型后，证明只有该模型启用且保存后立即切换 active；
- 使用当前 active Revision 执行无网络动态装配，确认错误不会在 Provider 请求前发生。

## 可逆性与回退

没有数据迁移。若未来重新引入本地能力门禁，必须先确定唯一能力事实源，并保证管理页面、Run Revision 与 Worker 使用同一
版本化 Profile；不得恢复两份数值的严格相等检查。
