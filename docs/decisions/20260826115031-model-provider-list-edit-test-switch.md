# ADR-20260826115031：模型供应商采用列表、统一编辑器、真实测试与显式切换

- 日期：2026-08-26
- 决策者：Runtime 维护者
- 关联任务/PR：改善后台模型配置的添加、测试、保存和切换体验
- 替代关系：部分替代 ADR-20260825180549 的“只保存并使用、不提供独立测试”页面流程；部分替代
  ADR-20260820095113 对内置与自定义 Provider 使用不同模型编辑方式的描述；延续 ADR-20260826000935 的
  “已保存 Revision 是运行时能力事实”和既有 Run 快照语义

- 被部分替代：[ADR-20260906195752](20260906195752-admin-task-oriented-configuration-and-publication.md)。第 4 条的只保存与两次请求保存并使用由原子保存接口替代；供应商列表、显式能力事实、独立真实测试、切换及托管快照继续有效。

## 背景

模型配置已经能保存不可变 Revision 并让新 Run 读取 active 配置，但日常页面仍有三个直接可用性问题：保存过的
Provider 不是可切换的工作列表，Pi Provider 只能选择目录已有模型，自定义 Provider 又只能填写很少的模型字段。
另外，原有连接探测只读取 `/models`；供应商已经开放但 Pi 目录尚未收录的新模型会被目录检查挡住，无法证明真实文本
生成是否可用。

`providerKey`、Revision、乐观锁和审计原因都是服务端实现细节。把这些字段要求管理员理解或填写，既不能提高模型调用
质量，也会增加把 API Key 误填到普通标识字段的风险。模型配置需要保留内部审计事实，但不需要人工安全审批流程。

## 决策驱动因素

- 保存过的多个 Provider 必须可见、可编辑、可测试和可来回切换；
- Pi 目录应减少录入，不得成为新模型的白名单或覆盖用户修改；
- 测试必须验证默认模型的真实文本生成，而不是只验证目录或网络连通；
- 模型能力、默认模型和密钥需要继续绑定不可变 Revision，保证已有 Run 不漂移；
- 页面不应暴露普通管理员无需理解的内部标识、Revision 和变更原因；
- 复用现有持久化结构，避免为页面重排引入数据库迁移或新的配置状态机。

## 备选方案

### 方案 A：保留单一“保存并使用”表单

实现最少，但管理员无法保存备用 Provider、单独测试或显式切换，不能解决配置管理问题，故不采用。

### 方案 B：以 Pi 目录作为模型白名单

元数据来源统一，但上游供应商发布新模型后必须等待 Pi 依赖升级，且管理员无法修正图片、推理和 Token 能力，故不采用。

### 方案 C：保存 Provider 列表、统一模型编辑器和独立真实测试

页面左侧展示最近保存的每个 Provider，右侧使用同一编辑器处理 Pi 与自定义 Provider。Pi 只填入初始值，显式保存值继续
进入 Revision。测试向默认模型发送受限文本请求；保存、测试和切换互相独立，并保留“保存并使用”快捷操作。

## 选择

采用方案 C，并固定以下边界：

1. 模型页展示当前生效状态和持久化 Provider 列表。每项显示名称、接口主机、默认模型、测试状态和当前使用状态，并提供
   编辑、测试、设为当前操作；页面不展示 Revision 历史。
2. 添加 Pi Provider 与添加自定义 Provider 使用同一个编辑器。`providerKey` 由系统生成或使用 Pi 稳定 ID，不作为表单
   字段；API Key 首次必填，编辑时留空复用当前 Revision 的加密凭据。
3. Pi 模型目录只提供初始值。模型 ID、显示名称、图片输入、推理、上下文窗口和最大输出都可编辑，也允许手工添加 Pi
   未收录模型。保存后只有默认模型启用，Worker 继续以 Revision 中的显式值为事实。
4. “保存”只创建新 Revision；“设为当前”只发布最近保存的 Revision；“保存并使用”在同一页面操作中依次完成两者。
   页面仅在发布成功并重新读取控制面后显示当前状态。模型配置的保存、测试和切换请求均不接收人工 `reason`，服务端用
   固定动作说明写入既有审计字段。
5. 模型测试使用对应 Revision 的托管密钥和默认模型，向 Base URL 下的 `chat/completions` 发送固定短文本，限制输出为
   最多 32 Token、禁用流式响应并设置 5 秒超时。只有成功响应包含 assistant 文本或 reasoning 文本时才记录健康；不再
   请求或依赖 `/models`。
6. 测试状态继续写入现有 Provider probe 记录，测试不自动保存或发布。模型测试不是切换门禁；记忆 Provider 的探测与
   发布门禁保持不变。
7. 发布仍原子切换 active Revision 并递增 generation。Worker 为首次处理的 Run 固定当前 Revision 和密钥；切换后的
   新 Run 使用新配置，已经开始的 Run 继续使用原快照，不要求重启 Worker。
8. 继续使用现有 Provider Revision、凭据密文、probe、activation 和 Run snapshot 表，不新增或修改 migration。

## 理由

这组交互直接对应管理员的四个动作：保存、验证、切换和查看当前状态。Pi 数据与显式配置分层后，新模型无需等待本地目录
升级；真实生成测试又比 `/models` 查询更接近实际可用性。内部 Revision 和审计仍保留恢复、并发和追踪能力，但不再成为
用户表单负担。

## 影响

- 后台模型页从单表单变为左侧 Provider 列表和右侧统一编辑器；
- 保存过的 Provider 可在刷新和进程重启后继续编辑、测试和切换；
- Pi 目录更新不会覆盖已经保存的模型能力；
- 模型探测会产生一次小额真实文本生成调用，且只验证文本路径，不验证图片能力；
- 错误地址、密钥或模型仍可被管理员跳过测试直接设为当前，后续 Run 会明确暴露 Provider 调用失败；
- “保存并使用”包含两个控制 API 调用；若发布失败，已保存 Revision 会留在列表中，但页面不会误标为当前，可重新切换；
- 不改变记忆 Provider、Skill 发布、数据库结构和已有 Run 的行为。

## 验证

- 协议测试覆盖显示名称正常大小写，以及模型保存、测试、切换请求拒绝额外 `reason`；
- Admin API 测试覆盖模型请求校验错误的安全说明，以及测试路由只使用服务端读取的 Revision；
- Provider probe 测试覆盖真实 `chat/completions` 请求体、默认模型、受限输出、非流式响应和无需 `/models`；
- Admin Web 测试覆盖自定义 Provider、Pi 初始值全字段修改、手工模型、保存/保存并使用、测试、切换和历史疑似密钥隔离；
- 既有 Worker 与持久化测试继续覆盖 active Revision、托管密钥和同一 Run 的配置快照。

## 可逆性与回退

本次没有迁移。页面可回退为单表单，真实探针也可恢复目录查询，但回退会重新失去备用 Provider 管理和目录外模型验证。
任何回退都不得删除已有 Revision、probe、activation 或 Run snapshot，也不得把托管密钥改回可读配置字段。
