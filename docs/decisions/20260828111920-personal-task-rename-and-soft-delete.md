# ADR-20260828111920：个人任务改名与软删除

- 状态：已接受
- 日期：2026-08-28
- 决策者：Runtime 团队
- 关联任务/PR：个人任务侧栏管理
- 替代关系：补充 ADR-0118、ADR-0140

## 背景

个人任务与团队任务已经按 Tenant 分开展示，但个人任务列表缺少直接管理入口。现有
`DELETE /v1/threads/:threadId` 的领域语义是归档：Thread、Run、Workspace、历史文件和审计事实继续保留。
由于大量运行数据通过 `ON DELETE RESTRICT` 复合外键引用 Thread，把“删除”实现为物理级联删除会扩大事务、
审计和恢复边界，也与既有归档命令冲突。

任务标题还可能由首条 durable 用户输入触发异步生成。如果用户手工改名后仍保留
`title_source='deterministic'`，已经排队或领取的标题生成任务可能覆盖用户选择。个人任务列表在当前活动空间为团队时
仍然可见，因此管理请求也不能误用当前团队的 `X-Tenant-ID`。

## 备选方案

### 方案 A：物理删除 Thread 及全部关联数据

符合字面删除，但需要定义 Run、Artifact、Resource、记忆、定时任务、分支来源和审计记录的级联或保留策略；
当前外键明确禁止这种隐式删除。

### 方案 B：继续使用归档作为删除语义，并从个人任务导航隐藏归档项

复用既有事务与授权边界，用户获得稳定的“从列表删除”结果，底层数据仍可用于审计和未来恢复。

### 方案 C：只在浏览器本地隐藏

无需服务端改动，但刷新或换设备后会重新出现，不能形成持久行为。

## 选择

采用方案 B，并补充以下约束：

1. 个人任务侧栏提供改名和删除操作；删除调用既有归档命令，成功后从个人任务列表移除。列表加载时也不展示
   `archived` Thread。
2. 新增 `PATCH /v1/threads/:threadId`，请求体只接受 1–200 字符的 `title`。该接口只允许 personal Tenant
   的 active Thread；团队 Tenant、无效 Membership、归档任务和不可见任务统一返回不存在。
3. 持久层改名命令按 Membership→Thread 的锁序重验 personal Tenant、Owner Membership 和 active 状态。写入标题时
   同时设置 `title_source='user'` 并推进 `title_generation_version`，已排队的异步标题不能覆盖用户改名。
4. 个人任务操作显式使用个人 Tenant 选择，不继承当前团队的 `X-Tenant-ID`。浏览团队任务时也可以管理侧栏中的个人任务。
5. 手工改名只改变 UI 标题。按照 ADR-0118 已冻结的第一阶段边界，已分配的历史文件目录不自动移动；
   `/thread-files` 继续使用与标题无关的稳定入口。

## 影响

- 正面：用户可以直接整理个人任务；删除在刷新后保持隐藏；用户标题不会被异步生成覆盖。
- 负面：删除不是物理擦除，当前也没有恢复已归档任务的用户界面。
- 安全：个人任务接口不向团队 Tenant 开放；授权失败继续使用 404，避免枚举任务或 Tenant 类型。
- 兼容：既有 DELETE 归档协议不变；新增 PATCH 是向后兼容扩展。团队任务原有归档行为不变。
- 数据：不新增迁移，不修改已执行 migration；复用现有 `title_source`、`title_generation_version` 和 Thread 状态列。

## 验证

- API 测试覆盖个人任务改名、标题规范化、空标题拒绝、团队任务拒绝和归档后拒绝。
- Web API 测试覆盖个人任务请求不携带当前团队选择器。
- Web 组件测试覆盖侧栏改名、删除确认、列表移除和归档任务过滤。
- 受影响包执行 typecheck、测试、格式与 lint 检查。

## 可逆性与后续

可以移除侧栏入口和 PATCH 路由而不迁移数据；已经写入的用户标题仍是合法 Thread 标题。若未来提供恢复功能，
应显式定义 archived→active 的权限、运行队列和历史导航语义。若未来要求隐私擦除，应另立 ADR，逐项定义关联数据的
保留、匿名化与删除顺序，不能把现有归档端点直接改成级联删除。
