# ADR-20260903171600：Demo 轨迹使用跨发布持久卷

- 状态：已接受
- 日期：2026-09-03
- 决策者：Runtime 维护者
- 替代关系：替代 [ADR-20260903152652](20260903152652-demo-trajectory-default-deployment.md) 中轨迹卷按 release ID 隔离、随旧 release 自动删除的结论

## 背景

Demo 轨迹查看器已经随 CD 默认部署，但首版 Compose 按 release ID 创建轨迹卷。应用每次发布都会挂载一个空卷，导致上一版本运行产生的轨迹从当前查看器中消失；这与 PostgreSQL、MinIO 等 Demo 持久数据跨应用发布保留的运维预期不一致。

用户不要求回填启用轨迹采集以前的历史 Run，但要求从本决策生效后的新 Run 开始，后续应用重新部署、失败回滚和旧 release 目录清理都不能清空已产生的轨迹。查看器展示协议、目录布局、管理员鉴权和 Worker 写入方式不需要改变。

## 决策

1. Worker 与 Trajectory 继续分别以读写和只读方式挂载同一 Compose 逻辑卷，容器内路径继续是 `/opt/hoox/model-wire-traces`。
2. 轨迹卷改为固定数据 epoch 名 `hoox-demo-trajectory-data-20260903`，不再包含 release ID。候选版本、当前版本和回滚版本始终挂载同一个卷。
3. 发布脚本清理旧 release 目录时不得删除稳定轨迹卷。自动发布不得执行 `down --volumes`，也不得根据 release ID 推导并删除轨迹数据。
4. 本次切换不回填旧的 PostgreSQL/MinIO 模型诊断记录，也不迁移首版 release 级轨迹卷；稳定卷开始启用后产生的轨迹才构成连续历史。
5. 未来如需清理或轮换轨迹，只能由维护者显式切换轨迹数据 epoch，并在独立保留策略、备份或脱敏方案确认后按确切旧卷名操作，不能绑定普通应用发布保留数量。

## 理由

固定数据 epoch 保持现有文件查看器和最小权限挂载边界不变，只调整卷生命周期。它避免给轨迹服务增加数据库凭据或历史回填逻辑，也使应用镜像回滚与诊断历史相互独立。显式 epoch 仍为将来的受控清理保留可逆手段。

## 影响

- 本决策生效前的轨迹和普通对话记录不会自动出现在查看器中。
- 本决策生效后，新 Run 写入的轨迹会跨 Demo 应用发布和回滚持续可见。
- 轨迹包含敏感正文并会持续占用磁盘；在独立保留清理消费者落地前，维护者需要监控稳定卷容量。
- `/trajectory/` 页面、API、管理员会话鉴权、文件格式和展示效果均不改变。

## 验证

- Compose 契约必须断言固定轨迹数据 epoch，且不得引用 `HOOX_DEMO_RELEASE_ID` 生成轨迹卷名。
- 发布脚本契约必须断言旧 release 清理不会删除稳定轨迹卷或 release 级轨迹卷。
- 使用同一命名卷先写入标记文件，再以不同 release 配置重建 Worker 与 Trajectory，确认标记文件和新轨迹仍可读取。
- CD 继续验证轨迹页面、匿名 API `401` 和管理员轨迹列表请求。

## 可逆性

可显式切换到新的轨迹数据 epoch，但切换前必须保留旧卷；回退应用镜像不需要切换轨迹卷。本决策没有数据库迁移和公开业务协议变化。
