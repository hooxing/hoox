## 背景与选择

运维需要在后台切换沙箱供应商、同时分配多个供应商，并按供应商性能设置模板和生命周期参数。启动时固定的默认供应商不能满足在线管理；只把默认 key 改成数据库字段又会使更新连接地址后的旧实例被发往新地址。

采用不可变供应商配置版本和独立路由配置。供应商配置包含连接地址、加密凭据、模板、运行 TTL、操作超时、生命周期超时、暂停保留时间及空闲 pause/kill 策略。后台只返回凭据是否配置，更新凭据通过独立写入字段；旧版本保留供既有实例恢复和回收。

路由支持单供应商和按权重分配。权重决定新建实例的比例，不承诺并发容量调度或自动性能学习。创建前固定路由结果和供应商配置版本，并将其与持久 registry 身份绑定；同一次创建的重试保持原选择。已有实例的恢复、Workspace 连接、终态处理和 Scheduler 清理读取绑定版本，不追随当前默认配置。切换或从新建池移除供应商不影响旧实例的清理能力。

未发布托管配置时兼容现有环境装配；已发布配置无法读取、解密或校验时失败关闭，不静默退回环境默认供应商。业务用户与模型不能修改路由或注入供应商参数。供应商能力差异继续由适配层约束，不能通过后台启用 AGS 不支持的到期自动暂停。

## 备选与理由

- 仅改环境变量：保持现状，但不能后台切换。
- 只存可变的当前供应商配置：实施简单，但旧实例在地址或凭据变化后失去可追溯的连接配置。
- 自动故障转移和按实时延迟选择：缺少稳定容量、成本和故障判定契约，创建结果未知时还可能产生重复实例；本决策只做显式权重分配。
- 采用不可变版本：需要持久绑定和清理链路改造，但可审计并保持远端身份一致。

## 验证与可逆性

必须验证后台鉴权、密钥不回显、版本并发冲突、配置发布、单供应商切换、权重分配、旧实例版本固定、进程重启后恢复、各供应商策略执行和 Scheduler 清理；运行真实沙箱与完整业务链路后，经过仓库 CI 门禁部署 Demo。

关闭新建路由不会删除旧配置与实例。回滚应用前需确认旧版本能处理新增持久绑定；迁移只向前，不能删除仍被实例引用的版本。部署失败保留数据和原实例，依照 Demo 恢复流程处理。
