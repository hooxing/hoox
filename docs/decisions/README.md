# 架构决策记录

本目录保存影响多个模块、持久数据、安全边界、公开协议或后续迁移成本的决策。ADR 解释“为什么选择当前方案”，不替代[当前架构文档](../architecture/overview.md)、代码和自动化测试。

## 阅读顺序

解释系统现状时，先读当前架构、参考和运维说明，再按需追溯 ADR。`catalog.md` 是完整历史账本，不能把其中一条“已接受”记录单独解释为当前行为；同一主题存在后续记录时，以替代关系和当前说明为准。

完全被替代、已废弃或已拒绝，且退出当前导航后更不易误读的 ADR 移入 `docs/archive/decisions`。完整目录继续保留其原日期、状态和链接；归档表示“不再指导当前实现”，不表示删除历史证据。

## 何时必须记录 ADR

满足任一条件时，在合并代码前新增 ADR：

- 改变 Tenant、Thread、Run、Workspace、Resource、Artifact、Sandbox 或 Skill 的所有权和生命周期；
- 改变 PostgreSQL、对象存储、Rollout、Outbox 或外部副作用的事实源与事务边界；
- 引入新的宿主机执行能力、凭据流向、网络出口、基础设施或第三方源码；
- 改变公开 API、事件、工具协议、错误码、恢复、幂等或兼容语义；
- 改变跨包依赖方向或需要高成本迁移的数据结构；
- 偏离已经接受的 ADR，或提前实现明确后置的能力；
- 在多个合理方案间选择，错误选择会造成跨模块返工、数据迁移或安全风险。

局部命名、文档修正、测试补充和可在单个提交内无损回退的实现细节，可以只在 PR 和提交说明中记录。

## 何时不应新建 ADR

以下内容默认不具有独立 ADR 价值：

- 单个缺陷的修复流水账，且选择可以在一个提交内无损回退；
- 仅记录“改了哪些文件、补了哪些测试”而没有长期约束或被放弃方案；
- 导航位置、像素、措辞、局部重试次数等实现参数，除非它们同时改变安全、协议、兼容或跨模块所有权；
- 已有 ADR 的直接实施切片，且没有改变原决策的边界、备选或回退方式；
- 已能由当前说明、代码和测试完整表达，并且未来维护者不需要知道“为什么不能采用另一个合理方案”的事实。

拿不准时，先把选择写进 PR；只有错误选择会造成跨模块返工、数据迁移、安全风险或长期兼容成本时，才升级为 ADR。同一决策的渐进实现优先更新当前说明和实施计划，不为每个修复提交追加一份 ADR。

## 编号规则

新 ADR 使用创建时的北京时间时间戳：

```text
YYYYMMDDHHmmss-english-slug.md
```

示例：

```text
20260820153000-public-documentation-architecture.md
```

标题使用：

```text
# ADR-20260820153000：中文标题
```

历史 ADR 使用四位编号或无编号文件名，其中 `0107`、`0152`、`0153`、`0154` 存在重复数字前缀。它们已经被提交、引用和替代，不进行破坏性改名；引用这些记录时必须使用带标题的文件链接，不能只写编号。新增记录不得继续使用四位递增编号。

## 决策流程

1. 复制[ADR 模板](adr-template.md)。
2. 写清背景和约束，不把偏好描述为唯一可能方案。
3. 至少列出两个备选；“暂不实现”通常也是有效备选。
4. 记录选择、理由以及未选择其他方案的原因。
5. 明确接口、数据、安全、运维、迁移和贡献者体验影响。
6. 指定可执行验证证据，例如契约测试、故障注入、指标或人工审阅。
7. 标明可逆性、回退窗口和一旦写入数据后不可逆的部分。
8. 在[决策目录](catalog.md)追加记录；若替代既有结论，在同一变更中更新前后记录的双向关系和状态。
9. 在 Issue、PR 和提交中引用 ADR；ADR 只有在存在可解析的真实链接时才添加相应关联字段，不保留空值或“待填写”占位。实现完成后把现行行为写入当前说明，不让 ADR 承担操作手册职责。

## 状态

| 状态 | 含义 |
| --- | --- |
| 提议 | 正在收集证据，不能作为已授权实现约束 |
| 已接受 | 已完成审阅，当前实现应遵守 |
| 部分已替代 | 只有正文明确列出的剩余结论仍然有效，必须链接替代记录 |
| 已拒绝 | 明确否决，保留原因供后续参考 |
| 已替代 | 结论被新 ADR 替代，历史记录仍保留 |
| 已废弃 | 对应能力已移除，不再适用于当前实现 |

状态只使用表中的六种名称；阶段、试验范围和替代摘要写在状态后的括号或独立关系字段中，不再创造“已采纳”“部分接受”“已被修订”等同义状态。

已接受 ADR 不应直接改写结论。需要改变时新增替代 ADR，并在新旧记录中建立双向链接。仍处于“提议”的 ADR 可以根据新证据更新；若后续 ADR 已经接受并实施其语义，旧提议必须关闭为“已替代”，不能长期与现行实现并存。

## 与其他文档的关系

- **当前架构文档**回答“系统现在是什么样”。
- **ADR**回答“为什么作出这个长期选择”。
- **实施计划**回答“准备按什么顺序完成”。
- **验证记录**回答“某个时间点执行过什么证据”。

当四者冲突时，不应让读者自行猜测：先核对代码和测试，再修正当前文档，并通过新的 ADR 记录需要改变的长期结论。

## 最小实施决策记录

不需要独立 ADR、但仍值得在 PR 中记录的选择，使用：

```text
背景：触发选择的事实和限制
备选：可行方案及代价
选择：采用的方案
理由：为什么此时选择它
影响：接口、数据、安全、运维和后续任务变化
验证：已有证据和合并后观察项
可逆性：如何回退，何时会变得难以回退
```
